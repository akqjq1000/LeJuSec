# 아키텍처

## 1. 상위 구조

LeJuSec는 **Control Plane(중앙 서버)** 과 **Agent(대상 시스템)** 의 2계층 구조이며,
둘 사이는 mTLS와 서명된 메시지로만 통신한다.

```
┌─────────────────────────────────────────────────────────────┐
│  Control Plane (중앙 서버)                                     │
│  ┌──────────┐  ┌──────────────┐  ┌────────────────────────┐  │
│  │ 자산/CMDB │  │ RAG 지식베이스 │  │ Orchestrator (LLM Agent)│  │
│  │(Postgres) │  │ (Vector DB)   │  │  · 도구 라우팅           │  │
│  └──────────┘  └──────────────┘  │  · 조치안 생성/판단       │  │
│  ┌──────────────────────────┐    └────────────────────────┘  │
│  │ 점검 기준/결과 버전 저장소  │    ┌────────────────────────┐  │
│  │ (DB + Git)                │    │ Sandbox Runner (K8s/VM) │  │
│  └──────────────────────────┘    └────────────────────────┘  │
└───────────────────────────────┬─────────────────────────────┘
                   mTLS / 서명된 작업 ↕ 서명된 결과
┌───────────────────────────────┴─────────────────────────────┐
│  Agent (대상 시스템) — Go 단일 바이너리                        │
│  수집(프로세스/파일/패키지) · 점검 실행 · FIM · self-protect   │
└───────────────────────────────────────────────────────────────┘
```

## 2. 컴포넌트

### 2.1 Control Plane

| 컴포넌트 | 책임 | 기술 |
|----------|------|------|
| API Gateway | 사용자 요청 수신, 인증/인가 | FastAPI |
| Orchestrator | LLM 기반 도구 라우팅·조치 생성·맥락 판단 | LangGraph + Claude |
| 자산/CMDB | 시스템 등록/해제, 메타데이터 | PostgreSQL |
| RAG 지식베이스 | 점검 기준·CVE 검색, 근거 제시 | Vector DB (Qdrant/pgvector) |
| 버전 저장소 | 점검 기준·설정 스냅샷 버전 | PostgreSQL + Git |
| 룰 엔진 | 합격/불합격 결정론적 판정 | Python (코드) |
| Sandbox Runner | 조치 격리 검증 | Docker/Firecracker |
| 작업 큐 | 에이전트 작업 분배 | NATS / Redis |

### 2.2 Agent

| 모듈 | 책임 |
|------|------|
| Collector | 프로세스·패키지·연관 파일 수집 |
| Scanner Runner | 선택된 점검 도구 실행 (OpenSCAP 등) |
| FIM | 파일 무결성 베이스라인·비교 |
| Self-protection | 에이전트 무결성·서명 검증 |
| Transport | mTLS + 서명 결과 전송 |

## 3. 핵심 데이터 흐름

### 3.1 점검 흐름

```
1. 사용자: 대상 시스템 점검 요청 (UI/API)
2. Control Plane: 자산 프로파일 조회 (CMDB)
3. Orchestrator(LLM): 프로파일 → 점검 도구 선택 (allowlist 내)
4. RAG: 관련 점검 항목 + 근거 검색
5. Agent: 작업 수신(서명 검증) → 수집 + 점검 실행
6. Agent: 결과 서명 → 전송 (mTLS)
7. 룰 엔진: 결정론적 합격/불합격 판정
8. 결과 + 근거 저장 (버전 저장소), 증적 서명 보관
```

### 3.2 조치 흐름 (HITL)

```
1. Orchestrator(LLM): 불합격 항목 → 조치안 + 롤백 스크립트 생성
2. 정적 분석: 파괴적 명령 차단
3. Sandbox Runner: 설정 스냅샷 복원 → 조치 적용 → 점검 재실행
4. 검증 리포트 + diff 미리보기 생성
5. [HITL] 담당자 승인/거부
6. 승인 시: Agent가 운영 반영 / 거부 시: 중단
```

## 4. 신뢰 경계

- **지시의 유일한 출처는 사용자(UI/API)**. 수집 데이터·웹 문서·로그는 데이터일 뿐 명령이 아니다.
- 에이전트↔서버는 mTLS + Ed25519 서명.
- LLM은 도구 레지스트리(allowlist) 밖 동작 불가.

자세한 위협·대응은 [위협 모델](design/threat-model.md) 참고.

## 5. 배포 토폴로지 (초안)

- Control Plane: Kubernetes (또는 단일 호스트 Compose, 초기 MVP).
- Agent: 대상 시스템에 단일 바이너리 배포 (systemd 서비스).
- Sandbox: Control Plane과 분리된 격리 노드/네임스페이스 권장.
