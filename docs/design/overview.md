# 설계 개요 및 실현 가능성

## 1. 목적

LeJuSec는 시스템 취약점 점검 전 과정 — 자산 식별, 점검 항목 선택, 점검 실행,
결과 판정, 조치안 생성, 검증 — 을 생성형 AI로 자동화한다.
목표는 "사람을 대체"하는 것이 아니라 **점검자의 판단을 보조하고 반복 작업을 제거**하는 것이다.

## 2. 설계 철학

### 2.1 결정론 우선, LLM 보조

AI에 과도하게 의존하면 오탐·환각으로 신뢰성이 무너진다. 역할을 명확히 분리한다.

| 결정론적 코드가 담당 | LLM이 담당 |
|---------------------|-----------|
| 데이터 수집 (프로세스/파일/패키지) | 수집 데이터 분류·추론 |
| 합격/불합격 판정 로직 | 점검 항목 선택·라우팅 |
| 해시·무결성 비교 | 조치 스크립트 생성 |
| 서명·암호화 | 변경 이벤트 맥락 판단 |
| 증적 보관 | 근거 문서 요약·제시 |

> **판정 로직을 LLM에 맡기지 않는다.** LLM 판정은 재현성이 없어 감사(audit)에 부적합하다.

### 2.2 Human-in-the-loop (HITL)

조치(remediation)의 **실제 운영 반영은 항상 사람 승인**을 거친다.
AI는 조치안 생성과 샌드박스 검증까지 수행하고, 적용 여부는 담당자가 결정한다.

### 2.3 최소 권한과 Allowlist

- 에이전트는 작업에 필요한 최소 권한만 보유.
- LLM은 **도구 레지스트리(허용된 도구 + 파라미터 스키마)** 안에서만 동작.
- LLM이 자유 형식 셸 명령을 생성·실행하는 경로는 존재하지 않는다.

## 3. 기능별 실현 가능성 요약

결론: **5개 기능 모두 구현 가능**. 단, 기능마다 AI 비중과 리스크가 다르다.

| # | 기능 | 실현성 | 접근 방식 |
|---|------|--------|-----------|
| 1 | RAG 점검 + 버전 관리 | 가능 (중심축) | 점검 기준 RAG + 자산 CMDB + 설정 스냅샷 Git 버전관리 |
| 2 | 프로세스/연관 파일 탐색 | 가능 | 패키지 매니저 결정론적 수집 + 소스설치는 `/proc`·`lsof`·systemd 분석, LLM 분류 보조 |
| 3 | 무결성/부정행위 탐지 | 가능 | 결정론적 FIM 본체 + LLM 맥락 판단 (실시간은 규칙·통계) |
| 4 | 도구 자동 선택 | 가능 | 대상 프로파일 → function calling 기반 도구 라우팅 |
| 5 | 조치 생성 + 샌드박스 검증 | 가능 (고위험) | LLM 생성 → 정적 분석 → 샌드박스 검증 → HITL 승인 |

각 기능의 상세 설계는 [features.md](features.md) 참고.

## 4. 범위와 가정

**대상 범위 (In scope)**
- Linux/Unix 서버 설정·패키지 취약점 점검 (KISA U-series, CIS, STIG 기준)
- 컨테이너 이미지·패키지 CVE 점검
- 조치안 생성 및 격리 검증

**현재 범위 외 (Out of scope, 추후)**
- Windows 서버 점검
- 웹 애플리케이션 동적 점검(DAST) 심화
- 실시간 침입 탐지(IDS/IPS) 대체

## 5. 규정 적합성

점검 목적이 KISA/ISMS-P 대응이라면 다음을 초기 설계에 포함한다.

- 점검 항목 ↔ 규정 조항 매핑 테이블
- 증적(evidence) 자동 수집·보관 (점검 시각, 원본 출력, 서명)
- 점검 결과 보고서 포맷 (기관 제출 양식 호환)
